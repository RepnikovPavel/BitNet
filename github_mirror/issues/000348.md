### Comment by @webpatser at 2026-04-28T10:26:19Z

Reproduced on Apple Silicon. Adding data points and a partial fix that affects modern macOS specifically.

## Reproduction

- Hardware: Apple M5 (10-core), 24 GB RAM
- OS: macOS 26 (Darwin 25.4.0)
- Compiler: Apple clang (Xcode CLT)
- Repo: HEAD `1f86f058` (current main, recursive submodules)
- Model: `microsoft/BitNet-b1.58-2B-4T-gguf`, `ggml-model-i2_s.gguf`
- Build: `python setup_env.py -md models/BitNet-b1.58-2B-4T -q i2_s`
- Inference: `python run_inference.py -m .../ggml-model-i2_s.gguf -p "The capital of the Netherlands is" -n 32 -t 10`

Output is incoherent token soup, identical symptom to #470 on Raspberry Pi 5 and #411 on Cortex-A53/A73:

```
The capital of the Netherlands is direct p developed anti unwittingline untreateduld left- Provincial exitscause fl race Royal lighten al traditionutin pin/divProvide promptly-int Urb failed disemb withdraw direct clearing coer
```

`system_info` reports `NEON = 0`, which is wrong for Apple Silicon.

## Two distinct bugs are conflated in this issue

### 1. NEON feature detection is broken on modern macOS

`ggml/src/ggml.c:3795` queries `hw.optional.AdvSIMD`, which was removed/renamed in recent macOS releases:

```
$ sysctl hw.optional.AdvSIMD
sysctl: unknown oid 'hw.optional.AdvSIMD'
$ sysctl hw.optional.neon
hw.optional.neon: 1
```

When the lookup fails, `has_neon` is set to 0 and the i2_s ARM kernel is bypassed entirely. Three-line patch:

```diff
--- a/ggml/src/ggml.c
+++ b/ggml/src/ggml.c
@@ -3795,7 +3795,9 @@ static void ggml_init_arm_arch_features(void) {
     int oldp = 0;
     size_t size = sizeof(oldp);
     if (sysctlbyname("hw.optional.AdvSIMD", &oldp, &size, NULL, 0) != 0) {
-        oldp = 0;
+        if (sysctlbyname("hw.optional.neon", &oldp, &size, NULL, 0) != 0) {
+            oldp = 0;
+        }
     }
     ggml_arm_arch_features.has_neon = oldp;
```

After this patch, `system_info` reports `NEON = 1`. Upstream `ggml-org/llama.cpp` already uses `hw.optional.neon` directly; this fork has drifted.

### 2. The CPU i2_s kernel itself produces garbage even with NEON enabled

After the patch above, `NEON = 1` but output is still incoherent:

```
The capital of the Netherlands is directebabdam new begin-all transmit Lorem record-conf et dispidar tick hit roundcoli Dien
```

This matches #470's bisect to commit `112f853` ("I2S kernels for weight & activation parallel on Intel & ARM"). The Pi 5 reporter confirms reverting that single commit restores correct output. The issue is independent of macOS-specific feature detection; #411 also documents int16 overflow concerns in the non-DOTPROD vmlal_s8 path. The NEON-detection fix is necessary but not sufficient.

## Workaround for Apple Silicon

Metal offload (`-ngl 999`) routes around the broken CPU kernel and produces correct output:

```
$ ./build/bin/llama-cli -m .../ggml-model-i2_s.gguf -ngl 999 -n 96 \
    -p "The capital of the Netherlands is"
... The capital of the Netherlands is Amsterdam. It is also known as the City of Flowers ...
```

`llama-bench` on M5 with Metal:

| test | t/s |
|---|---|
| pp256 | 682.55 ± 12.97 |
| tg200 | 42.12 ± 2.94 |

Peak RSS: 1.31 GB. The Metal kernels (`MUL_MV_I2_S_F32`, `MUL_MM_I2_S_F32` in `ggml/src/ggml-metal.m`) appear correct.

## Suggested next steps

1. Apply the NEON-detection fix above (small, self-contained, fixes Apple Silicon `system_info` reporting).
2. Track the kernel correctness regression separately under #470, which needs a kernel-level fix, not a feature-detection fix.

Happy to open a PR for the NEON-detection fix if useful.
