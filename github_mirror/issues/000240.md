@Zodijackyl98 Your AIs might be onto something there. The `GGML_COMPILER_SUPPORT_DOTPROD` `try_compile()` done by the `3rdparty/llama.cpp/ggml/src/CMakeLists.txt` first tests, if the `dotprod` extension is supported by the target system. If you are on a system with an `armv8.2-a+dotprod` arch, this should succeed and simply add the respective pre-processor define. If it fails (as it does on RPi 4B), we follow up with the `COMPILER_SUPPORTS_ARMV82_DOTPROD` test to see, if the *compiler* supports the `-march=armv8.2-a+dotprod` flag (so basically, if you could cross-compile for such a system). If that succeeds, we explicitly set the `-march=armv8.2-a+dotprod` flag (and thus are now basically cross-compiling for such a CPU). If you are on a `armv8-a` (like the RPi 4B) and your compiler supports cross-compiling for `armv8.2-a+dotprod` (which `clang-19` apparently does), you are now cross-compiling for such a system instead of compiling for your host system. Coincidentally, this `try_compile()` block was introduced in the "bad" commit.

Now, that I was explicitly looking for it, I actually saw the `-march=armv8.2-a+dotprod` given to the compiler. No wonder, it produces invalid instructions.

I think, the complete `COMPILER_SUPPORTS_ARMV82_DOTPROD` test needs to go. It only tests the cross-compile capability of the compiler, which doesn't help at all determining the capabilities of the target system:
